\begin{quote}
In secure program synthesis, specification elicitation has superseded code generation as the primary bottleneck \cite{Dodds2025Specs, QuinnHippel2026Proofs}. While executable oracles successfully restrict a model's ``degrees of freedom'' \cite{Regehr2026ZeroDOF}, formalizing subjective architectural quality to prevent unmaintainable ``vibecoding slop'' remains impractically expensive. We investigate whether informal engineering principles (e.g., the Zen of Python \cite{Peters2004Zen}) can function as zero-cost ``in-context oracles'' to enforce structural discipline. We introduce SlopBench, a benchmark curated to induce architectural degradation, and evaluate implementations across three frontier architectures (Claude 4.6, GPT-5.5, and Gemini 2.5 Pro). Our empirical results demonstrate that informal oracles consistently collapse structural degrees of freedom: conditioning yielded a 30--42\% reduction in mean cyclomatic complexity across all models. Crucially, this effect persists under deterministic decoding ($T=0$), indicating that soft oracles influence the model's highest-probability completions rather than merely shifting the mean of a sampled distribution. We further demonstrate that coupling these informal specifications with strict structural gates (e.g., Radon analysis) enables CEGIS-style feedback loops without the overhead of formal specification languages. To assess downstream maintainability, we introduced a chained maintenance stress test. At current benchmark complexities, a 3-step maintenance chain yielded a null result for functional failure: frontier agents successfully brute-force feature patches regardless of baseline structural debt. However, structural analysis reveals that oracle-constrained code maintains a measurably lower complexity across all context-ablated maintenance cycles. Ultimately, we demonstrate that informal specifications serve as pragmatic, scalable guardrails for enforcing code auditability, bridging the gap between ambiguous engineering taste and secure synthesis at mere prompt cost.
\end{quote}

\section{Introduction}

Current frontier language models excel at producing code that satisfies functional unit tests, effectively "solving" basic code generation benchmarks \cite{Chen2021HumanEval}. However, this functional success frequently masks a structural crisis: code that passes tests often manifests as deeply nested, monolithic, and unmaintainable "vibecoding slop." In the context of secure program synthesis (SPS), mathematical correctness guarantees and proof artifacts are insufficient if the resulting architecture is too structurally complex for a human to audit or safely maintain \cite{QuinnHippel2026Proofs}. If a reviewer cannot quickly comprehend the control flow of a synthesized module, the system remains practically insecure.

Addressing this structural degradation is fundamentally a specification problem. As the SPS community increasingly recognizes, specification elicitation has superseded code generation as the primary bottleneck \cite{VonHippel2026SPS}. While it is theoretically possible to write strict, formal rules against architectural slop, complete formal specifications rarely exist in practice, and formalizing subjective architectural taste is impractically expensive \cite{Dodds2025Specs}. We require a mechanism to constrain model outputs without the prohibitive overhead of formal verification.

Regehr \cite{Regehr2026ZeroDOF} argues that executable oracles---such as fuzzers and property testers---are necessary to collapse an LLM's "degrees of freedom" and prevent the generation of poor work. While these "hard" oracles are highly effective for enforcing functional constraints, they are computationally heavy and difficult to apply to qualitative structural metrics. We propose investigating "soft" in-context oracles: Can informal, universally understood engineering principles (such as the Zen of Python \cite{Peters2004Zen}) collapse structural degrees of freedom merely through prompt-level conditioning? Furthermore, can coupling these informal specifications with static structural gates instantiate formal Counterexample-Guided Inductive Synthesis (CEGIS) loops?

To rigorously evaluate this, we must move beyond static generation tasks and measure how structural complexity impacts downstream modification. We introduce a methodology that measures both static architectural degradation and dynamic maintainability via chained, multi-step maintenance stress tests, recognizing that code structure ultimately only matters if it affects the ability of subsequent agents (or humans) to safely modify the software.

Our core contributions are as follows:
\begin{enumerate}[label=\arabic*.]
    \item \textbf{SlopBench:} A 50-task pre-registered benchmark explicitly curated to induce architectural degradation, featuring chained maintenance stressors, custom domain-specific specifications, and independently verifiable human references.
    \item \textbf{SpecOracle:} An open-source evaluation pipeline integrating static analysis (Radon \cite{Radon}), isolated Dockerized execution, and structured LLM-as-a-Judge scoring \cite{Zheng2023Judge}.
    \item \textbf{\href{https://github.com/davidkimai/specoracle/blob/main/src/specoracle/stress.py}{SpecArena} Chained Ablation:} A rigorous downstream maintenance protocol designed to execute multi-step feature patches, isolating the true impact of code structure on subsequent agentic modifications over time.
    \item \textbf{Cross-Model Empirical Evidence:} A robust evaluation across three frontier models (Claude 4.6, GPT-5.5, Gemini 2.5 Pro) demonstrating a consistent 30--42\% reduction in cyclomatic complexity. Crucially, the persistence of this effect under deterministic decoding ($T=0$) confirms that soft oracles shift the model's preferred mode rather than merely its sampling variance.
    \item \textbf{CEGIS Hybrid Oracles:} A proof-of-concept demonstrating that executable structural gates can instantiate deterministic, formal feedback loops over informal specifications at zero formalization cost.
\end{enumerate}

\section{Related Work}

\textbf{Secure Program Synthesis and the Specification Bottleneck.} 
The transition from basic code generation to Secure Program Synthesis requires the simultaneous synthesis of software, specifications, and proofs \cite{VonHippel2026SPS}. However, as Dodds \cite{Dodds2025Specs} identifies, specification elicitation has become the primary bottleneck; complete, coherent formal specifications are rarely available in real-world systems. Furthermore, attempting to formalize the highly subjective rules of architectural "taste" and maintainability is impractically expensive. SpecOracle is designed to operate within this pragmatic gap, abandoning the quest for formal architectural proofs in favor of utilizing informal engineering principles as zero-cost structural guardrails.

\textbf{Executable Oracles and Degrees of Freedom.} 
Regehr \cite{Regehr2026ZeroDOF} posits that autonomous coding agents fail when granted the "degrees of freedom" to produce poor work, arguing that executable oracles (such as fuzzers and property testers) are required to pinch model outputs toward correctness. Our work directly tests the boundary conditions of this theory. While Regehr focuses on "hard" executable oracles, SpecOracle investigates the efficacy of "soft" in-context oracles. We aim to determine whether a non-executable, semantic constraint can still successfully collapse an LLM's structural degrees of freedom without the computational overhead of runtime validation machinery.

\textbf{Spec-Conditioned Decoding vs. In-Context Conditioning.} 
The SPS community has explored various methods to restrict model generation. For instance, Approximately Aligned Decoding \cite{Melcer2024AprAD} constrains LLM outputs directly at decode time, managing distribution distortion and ensuring constraint satisfaction. While powerful, this approach requires direct access to model weights or custom inference infrastructure. SpecOracle presents an ultra-accessible, application-layer alternative. By relying exclusively on in-context conditioning, we avoid manipulating logits and instead shape the context window, prioritizing qualitative structural metrics over hard constraint satisfaction.

\textbf{Agentic Evaluation and Dynamic Maintainability.} 
Our evaluation methodology builds upon the established code-generation tradition of HumanEval \cite{Chen2021HumanEval} and the qualitative LLM-as-a-Judge protocols inspired by MT-Bench \cite{Zheng2023Judge}. However, we extend these static methodologies by introducing a dynamic, agentic evaluation component. Rather than assessing code structure merely as a static aesthetic via complexity analyzers like Radon \cite{Radon}, we empirically measure its friction against a downstream autonomous agent. Our downstream maintenance context-ablation test represents a novel approach to evaluating the true cost of architectural slop in agentic workflows.

\section{Methods}

\textbf{Dataset: \href{https://github.com/davidkimai/specoracle/tree/main/data/slopbench}{SlopBench}.} 
We introduce \href{https://github.com/davidkimai/specoracle/tree/main/data/slopbench}{SlopBench}, a novel 50-task public benchmark curated specifically to induce architectural degradation rather than merely testing functional logic. To rigorously evaluate the limits of soft oracles, we structure our evaluation into three parts: (1) a locked 20-task pilot split (\href{https://github.com/davidkimai/specoracle/tree/main/data/slopbench_min}{\texttt{SlopBench-Min}}) to measure efficacy across multiple frontier models on tasks known to induce high baseline complexity; (2) an adversarial control to isolate semantic adherence from code-shortening bias; and (3) a full 50-task scale evaluation to identify boundary conditions.

\textbf{Generation Modes (Independent Variables).} 
We frame our generation protocol as a rigorous control-treatment experiment. In the \textbf{Baseline (Control)} condition, the language model receives only the functional specification ("vibecoding"). In the \textbf{Oracle (Treatment)} condition, the model receives the same prompt appended with a soft in-context constraint. In the \textbf{Hybrid (CEGIS)} condition, the model receives the informal specification coupled with static structural gates (e.g., Radon CC thresholds) that generate deterministic feedback loops for automated retries.

\textbf{Evaluation Pipeline (Dependent Variables).} 
Generated modules are executed as untrusted code within a strictly isolated, network-disabled Docker sandbox.
\begin{itemize}
    \item \textbf{Static Structural Metrics:} We utilize Radon \cite{Radon} to deterministically measure Cyclomatic Complexity (CC) and Nesting Depth. A secondary LLM-as-a-Judge \cite{Zheng2023Judge} scores qualitative adherence to the active informal specification.
    \item \textbf{Dynamic Maintainability (SpecArena v2):} To isolate the causal friction caused by architectural slop, we introduce a chained, multi-step context-ablation protocol. A maintenance agent implements sequential feature extensions against distinct context states to empirically measure whether clean static architecture actually improves downstream agentic maintainability over time.
\end{itemize}

\textbf{Reproducibility.} 
The evaluation pipeline natively orchestrates generation across Anthropic, OpenAI, and Google providers via the open-source \href{https://github.com/davidkimai/specoracle}{\texttt{specoracle}} CLI tool, ensuring full reproducibility of all cross-model findings.

\section{Results}

\subsection{Act 1. Cross-Model Generalization \& Deterministic Decoding}

Our first experiment establishes that soft, in-context oracles consistently enforce architectural discipline across varying model architectures and sampling regimes. Evaluated over the SlopBench-Min split, all three frontier models (Claude 4.6, GPT-5.5, Gemini 2.5 Pro) demonstrated significant 30--42\% reductions in mean Cyclomatic Complexity.

Crucially, this structural compression persists even under deterministic decoding. When GPT-5.5 was forced to output its single most-preferred completion ($T=0$), the oracle still drove cyclomatic complexity down by 41.7\%. This indicates that soft oracles do not merely sample simpler variants from the tail of a probability distribution; they fundamentally shift the model's highest-probability preferred mode toward structural simplicity, with only minor functional degradation (Pass@1 dropping from 96.7\% to 93.3\%).

\subsection{Act 2. The CEGIS Bridge via Hybrid Oracles}

To test whether informal specifications can instantiate formal feedback loops, we evaluated a CEGIS-inspired Hybrid Oracle. This pipeline couples an informal specification prompt with strict structural gates (e.g., Radon CC > 8). If the gate fails, the system generates deterministic feedback citing the specific violating functions.

On a proof-of-concept run, the Hybrid Oracle triggered retries on 55\% of tasks. Across all retried tasks, the automated feedback loop successfully forced the model to simplify its architecture (average reduction of 4.0 CC points) until every artifact passed the strict complexity gate. This demonstrates that executable structural gates can effectively anchor informal specifications, bridging the gap between ambiguous engineering taste and deterministic security constraints at zero formalization cost.

\subsection{Act 3. Chained Maintenance: The Epistemic Null}

To assess whether this static structural rigor improves dynamic downstream maintainability, we subjected the generated code to a 3-step chained maintenance stress test via SpecArena v2. 

At the current SlopBench-Min complexity scale, we observe an epistemically honest null result for functional failure: \texttt{THRESHOLD\_FOUND: False}. The frontier maintenance agent successfully brute-forced sequential feature patches with near-perfect success regardless of whether it operated on oracle-constrained code, vibecoded slop, or a completely ablated context stub. However, structural data reveals a persistent advantage: across all 3 context-ablated maintenance cycles, the oracle-conditioned code maintained a cyclomatic complexity $\sim$1.2 points lower than the unconstrained baseline. While current agentic evaluations mask the true friction of technical debt, the structural divergence remains measurable.

\subsection{Act 4. Semantic Adherence Control}

To confirm models respond to specification semantics rather than a generic pressure to "write less code," an adversarial control task (\texttt{045\_adversarial\_spec}) mandated the use of explicitly labeled branch variables. The model complied entirely, turning a simple lookup (Baseline CC = 1.0) into a massive cascade of branches (Oracle CC = 19.0). This indicates strict adherence to the in-context semantic constraint even when it conflicts with structural simplicity.

\subsection{Act 5. Boundary Conditions at Scale (50 Tasks)}

To identify where soft oracles cease to be effective, we scaled the evaluation to the full 50-task benchmark. On this broader set, the aggregate CC reduction weakened significantly to a mean delta of -0.953. Rather than a replication failure, this reveals a critical boundary condition: the 30 new tasks possessed much lower baseline complexity (mean CC $\sim$4.5). When code is already structurally simple, soft oracles face diminishing returns because there are fewer degrees of freedom to collapse. Soft oracles are primarily effective as a defense mechanism against inherently complex architectural tasks.





\section{Discussion}

Our empirical evaluation yields two critical insights for the Secure Program Synthesis community. First, we demonstrated that the specification bottleneck can be pragmatically mitigated using soft in-context oracles. Across three frontier architectures, conditioning on informal engineering principles collapsed the structural degrees of freedom, yielding consistent 30--42\% reductions in cyclomatic complexity. Crucially, the persistence of this effect under deterministic decoding ($T=0$) confirms that informal oracles shift the core structural mode of the model's preferred output. Furthermore, the implementation of our CEGIS-inspired Hybrid Oracle proves that informal specifications can be successfully anchored by hard, executable structural gates to create deterministic feedback loops at zero formalization cost.

Second, our SpecArena chained context-ablation test revealed a notable characteristic of current frontier models: they are highly robust to architectural slop during short-horizon maintenance tasks. Because the maintenance agent successfully brute-forced 3 sequential feature patches on highly complex baseline code, we report a null result for functional failure. However, this exposes a critical blind spot in agentic evaluations. If frontier models can mask the friction of technical debt during short chains, "pass/fail" functional tests are fundamentally insufficient for measuring secure architecture. If reviewers rely solely on test success, architectural slop will silently accumulate until it exceeds the model's reasoning bounds, rendering the system practically insecure and entirely un-auditable by humans. 

\subsection{Limitations}

We acknowledge several limitations in our current study. Most critically, our scale evaluation revealed an \textbf{Aggressive Conditioning Failure Mode}: on five of the advanced architectural tasks (e.g., circuit breakers, event correlators), oracle conditioning caused a 100\% failure rate on functional tests across all samples. The model adhered so strictly to structural decomposition that it over-abstracted and broke the underlying logic. This demonstrates the hard limits of soft oracles: overly aggressive structural conditioning can compromise functional correctness.

Second, our 3-step maintenance chain was insufficient to locate the functional failure threshold of frontier models; the models possessed enough zero-shot capability to patch features regardless of baseline structural debt. Finally, the evaluation is currently restricted to Python. Python's inherent emphasis on readability and the likely pre-training ubiquity of the "Zen of Python" might make in-context structural oracles artificially effective compared to potential performance in denser, less semantically constrained languages like C++ or Rust.

\subsection{Future Work}

Future work must scale the SpecArena infrastructure to execute deep-chain threshold hunting (e.g., 10--20 step maintenance chains) to empirically identify the exact complexity threshold where an LLM's reasoning undergoes a catastrophic collapse on toxic architecture. Additionally, the CEGIS-inspired Hybrid Oracle pipeline should be integrated directly into native evaluation ecosystems, such as the UK AISI \texttt{inspect\_evals} framework, to test structural gating mechanisms at scale.

\section{Conclusion}

We investigated whether informal engineering principles could serve as structural guardrails in the secure program synthesis pipeline. The cross-model results demonstrate that soft in-context oracles consistently collapse structural degrees of freedom without sacrificing functional correctness. By pairing these informal specifications with executable structural gates, we instantiated a CEGIS-style feedback loop that dramatically improves code quality. While frontier models are robust enough to brute-force short-term maintenance on degraded code---highlighting a dangerous blind spot in standard functional evaluations---the structural data confirms that oracle-conditioned code maintains a measurable complexity advantage across maintenance cycles. Enforcing structural discipline at the prompt level remains a vital, zero-cost necessity for ensuring the long-term human auditability and security of synthesized software.
